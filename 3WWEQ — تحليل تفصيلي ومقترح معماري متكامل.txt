3WWEQ — تحليل تفصيلي ومقترح معماري متكامل
حالة المستند: مقترح للمراجعة والموافقة — لا يتضمن كود تنفيذي. ملاحظة تسمية: المستودع يعتمد 3WWEQ في PRODUCT.md وapp/layout.tsx، بينما طلبك يكتب 3WEEQ. سأستخدم 3WWEQ في هذا المستند، ويجب حسم الاسم نهائياً قبل الدومين والفوترة والعلامة التجارية.

0. الحكم التنفيذي
المشروع الحالي ليس متجراً؛ هو واجهة سينمائية عالية الجودة لمنتج واحد، بدون أي طبقة تجارة أو بيانات أو مصادقة أو دفع. البنية المقترحة يجب أن تحافظ على هذه الواجهة كما هي، وتبني تحتها نواة تجارة مستقلة (Headless Commerce Core) قابلة للتوسع من منتج واحد إلى آلاف المنتجات، ومن موقع واحد إلى ويب + تطبيق + نقاط بيع.

القرارات الخمسة الحاسمة:

الواجهة: Next.js 16 App Router الحالي، مع إعادة هيكلة Routes إلى [locale] وRoute Groups، وعدم إعادة بناء التصميم.
النواة التجارية: Medusa v2 كـ Modular Commerce Core على Node/TypeScript، بدلاً من بناء NestJS من الصفر أو الاعتماد على BaaS/CMS كمتجر.
قاعدة البيانات: PostgreSQL (Neon أو Supabase Postgres) + Redis للحالات المؤقتة والطوابير.
المحتوى التحريري: Sanity للقصص والمجلة والحضارات فقط، وليس لبيانات السعر أو المخزون أو الطلبات.
البنية: Modular Monolith منظم حسب Domain-Driven Design، وليس Microservices في الإطلاق.
المدة التقديرية للوصول إلى بيع RAFID: 10–14 أسبوعاً، منها 1–2 أسبوع تأسيس و4–6 أسابيع MVP.

2. المبادئ المعمارية والقرارات الأساسية
2.1 المبادئ
Modular Monolith أولاً: كل Domain وحدة مستقلة داخل تطبيق واحد. لا Microservices قبل أن تثبت الحاجة التشغيلية.
الخادم هو مصدر الحقيقة: السعر، المخزون، الخصم، والطلب لا تُحسب في المتصفح أبداً.
API-First: المتجر، التطبيق، ونقاط البيع تستهلك نفس الـ APIs.
PostgreSQL هو Source of Truth: البحث والكاش والتحليلات نسخ مشتقة، وليست مصادر حقيقة.
Event-Driven Side Effects: البريد، الواتساب، نقاط الولاء، والتحليلات تتم عبر Outbox/Queue، وليس داخل طلب الدفع.
Idempotency في كل عملية مالية: إنشاء الطلب، الدفع، الاسترداد، والـ Webhooks.
الخصوصية والأمان بالتصميم: لا تخزين بطاقات، أقل قدر من PII، وتشفير الحقول الحساسة.
i18n وRTL مكوّنان أساسيان: ليسا طبقة ترجمة فوق نظام إنجليزي.
ميزانيات أداء ملزمة: LCP < 1.8s على 4G، INP < 200ms، CLS < 0.05، JavaScript أقل من 200KB على صفحة المنتج.
اشترِ Commodity وابنِ التمايز: لا تبنِ محرك دفع أو بحث من الصفر؛ ابنِ تجربة العميل والقصص.

المبادئ:

next/image مع Loader مخصص لـ Cloudinary لاحقاً، وnext/font/local أو الإبقاء على @font-face الحالي مع preload.
لماذا لا نستخدم Shopify/Theme: تجربة العلامة سينمائية ومخصصة، وفريق الواجهة موجود. لكن يجب ألا تتحول الواجهة إلى مصدر منطق تجاري.

القرار: Medusa v2 كـ Commerce Core، مع بناء Custom Modules للحضارات، قوائم الانتظار، الولاء، والـ Clienteling. هذا يحقق DDD عملياً: كل Bounded Context وحدة مستقلة بعقود واضحة، لكنها تعمل داخل عملية واحدة قابلة للنشر.

لماذا هو الأنسب للعلامة الفاخرة:

تحكم كامل في تجربة الدفع بدون قيود SaaS.
ملكية بيانات العميل والطلب.
دعم Multi-region وMulti-currency وSales Channels من البداية.
إمكانية إضافة نقاط بيع (POS) وتطبيق جوال على نفس الـ API.
قابلية بناء Workflows خاصة: تخصيص، تغليف هدايا، موافقة يدوية على الطلبات عالية القيمة، إطلاق محدود.
المحتوى التحريري: Sanity للمجلة، قصص الحضارات، وصفحات الحملات. بيانات المنتج التجارية (السعر، SKU، المخزون، الحالة) تبقى في Medusa. إذا احتاج المحرر نصاً طويلاً للمنتج، نستخدم جدول ترجمة داخل Medusa أو كتلة Sanity مرتبطة بمعرّف المنتج، مع بقاء السعر والمخزون في Medusa فقط.

A.3 قاعدة البيانات
الاختيار: PostgreSQL.

الأسباب:

الطلبات، المدفوعات، الاستردادات، والمخزون تحتاج ACID وقيوداً علائقية.
العلاقات كثيرة: منتج ← متغير ← سعر ← مخزون ← طلب ← دفع ← شحن ← مرتجع.
تقارير المتجر (AOV، Sell-through، Refund Rate) أسهل بكثير في SQL.
JSONB يمنح مرونة للخصائص المتغيرة (النوتات العطرية، الأبعاد، المواد) دون التضحية بالعلاقات.
Postgres يدعم SELECT FOR UPDATE وقيود CHECK وpartial indexes، وهي ضرورية لمنع البيع الزائد في الإصدارات المحدودة.
الاستضافة: Neon (فرعيات قاعدة بيانات، Serverless، PITR) أو Supabase Postgres إن أردت لوحة تحكم موحدة. المهم: نفس المنطقة الجغرافية قدر الإمكان مع خادم Medusa، وPgBouncer للاتصالات.

Redis: Upstash أو Redis مُدار، للجلسات، rate limiting، أقفال المخزون المؤقتة، والطوابير.

البحث: Meilisearch في البداية (دعم جيد للعربية والأخطاء الإملائية والفلاتر)، والانتقال إلى Algolia عند الحاجة العالمية. فهرس البحث يُبنى من أحداث Medusa، وليس مصدر حقيقة.

A.4 المصادقة
الاختيار الموصى به: مصادقة أصلية داخل Medusa + OTP للهاتف + Magic Link للبريد، بدون كلمات مرور افتراضية.

التفاصيل:

Guest Checkout إلزامي. لا نجبر العميل على إنشاء حساب لشراء عطر واحد.
OTP عبر Unifonic أو Twilio Verify أو Msegat، بحد 5 دقائق وصلاحيات محاولات صارمة.
الجلسات عبر Cookies آمنة HttpOnly + Secure + SameSite=Lax، مع تدوير الجلسة وإمكانية الإبطال.
ربط حساب الضيف بالحساب بعد الشراء عبر البريد أو الهاتف.
Passkeys لاحقاً كخيار للعملاء الدائمين.
لوحة الإدارة: 2FA إلزامي + RBAC + سجل تدقيق.
البدائل:

Clerk: أفضل بديل مُدار (Phone OTP، Passkeys، حماية Bots، DX ممتاز)، لكنه يضيف تكلفة وتبعية ومزامنة هوية مع Medusa.
Auth0: قوي للمؤسسات لكنه مكلف ومعقد لمشروع بهذا الحجم.
Supabase Auth: مناسب فقط إذا اخترت Supabase كمنصة بيانات، ويبقى الربط مع Medusa عبئاً إضافياً.
الحكم: ابدأ بـ Medusa Auth + OTP مخصص. انتقل إلى Clerk فقط إذا أصبحت إدارة الهوية عبئاً تشغيلياً.

قواعد التنفيذ:

لا تمر بيانات البطاقة عبر خوادمنا. نستخدم Hosted Fields / Payment Elements / Redirect + 3DS، ونحقق PCI-DSS SAQ A.
Multi-currency: سعر العرض بالعملة المحلية (SAR/AED/KWD/QAR/USD/GBP/EUR)، مع price_list لكل سوق، وتحويل يومي لأسعار الصرف، وتثبيت السعر عند بدء الدفع لمدة 15 دقيقة.

3DS / SCA: إلزامي حيث ينطبق، مع التعامل مع فشل التحدي وإعادة المحاولة.
الاحتياط: إذا فشل مزوّد، نعرض مزوّداً بديلاً دون فقدان السلة.
التسوية: تقرير يومي لمطابقة مدفوعات المزوّد مع الطلبات، وكشف الفروقات تلقائياً.

Part B — نموذج البيانات والـ ERD
B.1 قواعد النمذجة
المبالغ أعداد صحيحة (Minor Units): amount_minor وليس float. العملة مخزنة صراحةً.
Snapshots في الطلبات: نحتفظ باسم المنتج والسعر والعنوان وقت الشراء، حتى لو تغيّر المنتج لاحقاً.
Soft Delete: deleted_at للمنتجات والعملاء، مع منع الحذف النهائي للطلبات المالية.
Translation Tables: كل نص قابل للترجمة له جدول ترجمة مستقل، وليس JSONB فقط.
Idempotency Keys: على إنشاء الطلب، الدفع، الاسترداد، والـ Webhook.
Audit Log: كل تغيير إداري حساس له سجل غير قابل للتعديل.
لا حذف للأسعار القديمة: valid_from / valid_to للحفاظ على التاريخ المالي.

Part C — رحلة العميل وتدفق البيانات
C.1 التصفح والاكتشاف
المسار: GET /ar/products/rafid → Next.js Server Component → Medusa Store API → Cache Components.

آلية Next 16:

تفعيل cacheComponents: true في next.config.ts.
استخدام use cache + cacheLife('hours') + cacheTag('product:rafid') لصفحة المنتج.
عند نشر المنتج من Medusa أو Sanity، يُستدعى Webhook إلى /api/revalidate ينفذ revalidateTag('product:rafid').
الصفحة تُبنى كـ Static Shell (الصور، النصوص، السعر الأساسي)، والـ Cart/Stock/Recommendations تُحمَّل كـ Dynamic Islands عبر Suspense.
لا نستخدم ISR بالمعنى القديم فقط؛ النموذج الجديد يحقق نفس النتيجة مع تحكم أدق.
البحث: /api/search على الخادم → Meilisearch. لا يُعرَّض مفتاح البحث في المتصفح. دعم الأخطاء الإملائية العربية وتطبيع الألف والهمزة والتاء المربوطة.

بطاقة المنتج: صورة واحدة مهيمنة، السعر بالعملة المحلية، حالة المخزون، شارة "Limited Edition" عند الحاجة، وزر "اكتشف رافد".

C.2 السلة
القرار: Server-side Cart هو المصدر الوحيد للحقيقة.

عند أول إضافة، Medusa ينشئ Cart ويعيد cart_id.
cart_id يُخزَّن في Cookie: HttpOnly, Secure, SameSite=Lax, مدة 30 يوماً.
Zustand يحتفظ بحالة واجهة متفائلة (عدد القطع، فتح Drawer)، لكنه لا يحسب السعر النهائي.
عند تسجيل الدخول، يتم دمج سلة الضيف مع سلة الحساب.
كل عملية إضافة/تعديل تعيد التحقق من السعر والمخزون والحد الأقصى للعميل.
لا يتم تخزين الأسعار أو المخزون في localStorage.
Guest Checkout: مسموح بالكامل. لا نطلب حساباً إلا بعد إتمام الشراء، ونعرض إنشاء حساب اختياري مع حفظ العنوان.

السلة المتروكة: Workflow بعد 1 ساعة و24 ساعة، مع احترام الموافقة التسويقية، وروابط استئناف آمنة.

C.3 الدفع (Checkout)
الخطوات:

Contact: بريد + هاتف E.164. OTP اختياري لاستئناف السلة أو التحقق من العميل.
Address: إدخال يدوي + Address Autocomplete (Google Places/Loqate) مع تحقق من صحة العنوان.
Shipping: حساب الخيارات عبر Aramex/DHL/SMSA. السعر حسب الوزن الحجمي، الوجهة، والتأمين.
Tax & Duties: حساب VAT حسب الدولة. للخليج: أسعار شاملة الضريبة (DDP). للخارج: DAP مع توضيح الرسوم الجمركية.
Payment: اختيار البطاقة، Apple Pay، Google Pay، mada، KNET، أو BNPL إن فعّل.
Review: ملخص نهائي، شروط البيع، سياسة الإرجاع، وتأكيد الطلب.
قواعد حرجة:

إنشاء الطلب يتم بـ Idempotency Key لمنع التكرار عند إعادة المحاولة.
حجز المخزون يتم قبل إنشاء جلسة الدفع، ويُحرَّر تلقائياً بعد 15 دقيقة إذا لم يكتمل الدفع.
السعر يُعاد حسابه على الخادم لحظة الدفع؛ أي تغيير يُعرض للعميل قبل التأكيد.
لا يُعتبر الطلب مؤكداً إلا بعد تأكيد الدفع من الـ Webhook، وليس من رد المتصفح.
التحقق من العنوان والهاتف و3DS يقلل الاحتيال، مع مراجعة يدوية للطلبات عالية القيمة.
الشحن الدولي:

GCC: Aramex + DHL Express + SMSA (السعودية) + Emirates Post.
Global: DHL Express مع HS Code وبيان جمركي.
العطور الكحولية: سلعة خطرة (UN1266)؛ يجب التحقق من قيود كل ناقل ودولة قبل عرض السعر. بعض الدول تمنع الشحن الجوي للعطور الكحولية.
DDP vs DAP: DDP للخليج لتجربة فاخرة بلا مفاجآت جمركية، وDAP للأسواق العالمية مع إفصاح واضح.

قواعد الـ Webhook:

التحقق من التوقيع على Raw Body قبل أي تحليل.
تخزين event_id في webhook_event مع قيد فريد لمنع المعالجة المزدوجة.
الرد بـ 200 سريعاً ثم المعالجة في Queue.
دعم الأحداث المتأخرة أو غير المرتبة عبر State Machine محصّن.
إعادة المحاولة مع Backoff، ثم Dead Letter Queue ومراجعة يدوية.
تسوية يومية بين مزوّد الدفع والطلبات، لكشف المدفوعات اليتيمة أو المفقودة.
مصفوفة الفشل:

الحالة	السلوك

مبلغ غير مطابق	تجميد الطلب ومراجعة يدوية

استرداد جزئي	Ledger منفصل وتحديث حالة الدفع

C.5 ما بعد الشراء
تأكيد الطلب خلال 60 ثانية: بريد + واتساب (إن وافق العميل).
معلومات الشحن مع رقم التتبع ورابط الناقل.
التغليف: تعليمات العناية، بطاقة القصة، QR لتجربة unboxing رقمية.
بعد التسليم: طلب تقييم بعد 7 أيام، فقط للمشتري الموثّق.
الولاء: إضافة النقاط بعد انتهاء فترة الإرجاع (وليس عند الشحن) لتجنب الاحتيال.
الإرجاع: RMA خلال 14 يوماً للعبوات غير المفتوحة، مع استثناءات صحية واضحة.
إعادة الشراء: تذكير ذكي بعد استهلاك تقديري، دون إزعاج.

AOV	إجمالي الإيراد / عدد الطلبات
Cart Abandonment	سلات غير مكتملة / سلات منشأة
Checkout Abandonment	بدأ الدفع ولم يكمل / بدأ الدفع
Sell-through	المبيع / المتاح في الإصدار
Waitlist Conversion	المسجلون الذين اشتروا / المسجلون
Refund Rate	قيمة الاسترداد / الإيراد
Return Rate	المرتجعات / الطلبات
Repeat Rate	عملاء اشتروا أكثر من مرة / العملاء
LTV	القيمة المتوقعة للعميل
VIP Share	نسبة الإيراد من الشرائح العليا
Contribution Margin	الإيراد − تكلفة المنتج − الشحن − الدفع − الإرجاع
التنفيذ: أحداث خادمية (Server-side) عبر Medusa Events + GA4 Measurement Protocol + Meta CAPI، مع Consent Mode. لا نعتمد على Pixel فقط بسبب Ad Blockers وiOS.

Part E — الميزات المتقدمة والاستعداد للمستقبل
E.1 تعدد اللغات وRTL
العربية افتراضية، الإنجليزية ثانوية: /ar/... و/en/....
proxy.ts يكتشف اللغة من المسار أو Accept-Language ويحوّل.
next-intl للـ UI Messages، وجداول ترجمة في قاعدة البيانات للمنتجات والمحتوى.
dir يُضبط في Layout حسب اللغة، وليس عبر CSS معكوس.
Slugs مترجمة مع 301 من القديم إلى الجديد.
hreflang وSitemap لكل لغة، وCanonical صحيح.
تنسيق العملة والتواريخ عبر Intl، مع خيار التقويم الهجري إن رغب المالك.
العربية: ممنوع letter-spacing، وتطبيع البحث (أ/إ/آ، ة/ه، التشكيل).
البريد والواتساب: قوالب RTL منفصلة، وليس ترجمة آلية.
العملة مستقلة عن اللغة: عميل عربي في لندن قد يرى GBP.
E.2 الطلبات المسبقة وقوائم الانتظار
Waitlist مزدوجة التأكيد (Double Opt-In) لكل حضارة/منتج/إطلاق.
تسجيل بدون حساب، مع بريد أو هاتف.
أولوية اختيارية للإحالات، ونافذة وصول مبكر.
إشعارات بريد/واتساب عند فتح الإطلاق، مع أكواد فريدة.
Drop Mechanics: كمية محددة، حد لكل عميل، Waiting Room عند الذروة، وBot Protection.
Pre-order: عربون أو كامل، تاريخ شحن متوقع، وسياسة إلغاء واضحة.
قياس التحويل من Waitlist إلى شراء، وليس فقط عدد التسجيلات.
E.3 نظام VIP والولاء
شرائح: Sand → Gold → Royal (أو أسماء من هوية العلامة).
نقاط لكل عملة، باستثناء الخصومات والإرجاع.
مزايا: وصول مبكر 24 ساعة، شحن سريع مجاني، تغليف خاص، هدايا ميلاد، دعوات إطلاق، وخدمة Clienteling.
Ledger غير قابل للتعديل، مع انتهاء صلاحية النقاط وسجل تدقيق.
لا تُعرض الخصومات علناً؛ الولاء تجربة خاصة وليس "خصم 20%".
ربط الولاء بـ Medusa Customer Groups وPromotions، وليس نظاماً منفصلاً.
E.4 لماذا Headless؟
الواجهة السينمائية تحتاج حرية كاملة لا توفرها منصات الـ Themes.
نفس الـ API يخدم الموقع، التطبيق، ونقاط البيع.
إمكانية إضافة Storefront جديد أو سوق إقليمي دون تكرار النواة.
فصل المحتوى عن التجارة يسمح للفريق التحريري بالعمل دون لمس الأسعار.
ملكية البيانات تسمح بالتحليلات المتقدمة وCRM وClienteling.
قابلية استبدال أي مزوّد (دفع، شحن، بحث) عبر Adapters.
التكلفة: تحتاج فريقاً هندسياً وDevOps. لهذا نبدأ بـ Modular Monolith وليس Microservices، ونستخدم خدمات مُدارة.

E.5 Omnichannel
Mobile App: React Native/Expo لاحقاً، يستهلك نفس Store API ونفس المصادقة.
POS: Medusa Sales Channels + Stock Locations؛ بيع في Pop-up، خصم من نفس المخزون، وربط الطلبات بالعميل.
Clienteling: ملف عميل موحد، تفضيلات، تاريخ الشراء، وملاحظات المستشار.
BOPIS / Same-day: لاحقاً حسب شراكات الشحن.

F.4 القانون والامتثال
الخصوصية: GDPR (للعملاء الأوروبيين)، CCPA (كاليفورنيا)، UAE PDPL، Saudi PDPL.
الموافقات: Cookie Consent منفصل عن التسويق؛ Analytics لا يعمل قبل الموافقة.
DSAR: تصدير وحذف بيانات العميل خلال المدة القانونية.
DPA مع كل مزوّد يعالج بيانات شخصية.
الشروط: Terms of Service، Privacy Policy، Shipping Policy، Returns/Refund Policy، Cookie Policy.
الضرائب: تسجيل VAT في السعودية/الإمارات حسب الحد، وفاتورة متوافقة مع الفاتورة الإلكترونية (ZATCA في السعودية) عند الحاجة.
تنظيم العطور: IFRA، تسجيل/إشعار مستحضرات التجميل (SFDA في السعودية، ESMA/MOHAP في الإمارات)، ملصقات عربية، رقم التشغيلة، تاريخ الانتهاء.
الشحن: تصنيف العطور الكحولية كبضائع خطرة، MSDS، وقيود الناقلين والدول.
العمر: 18+ لبعض الأسواق إن لزم.
F.5 السعة: ماذا يحدث عند بيع 10,000 عطر في ساعة؟
الحساب:

10,000 طلب/ساعة = 2.8 طلب/ثانية تقريباً. هذا رقم متواضع لـ PostgreSQL إذا صُممت الفهارس والـ Transactions بشكل صحيح.
عنق الزجاجة الحقيقي ليس API، بل:
تنازع المخزون على الإصدار المحدود.
حدود مزوّد الدفع (Rate Limits).
الحمل المتزامن على صفحة الإطلاق (قد يكون 100,000 زائر في نفس الدقيقة).
الحلول:

حجز مخزون ذري + طابور + Waiting Room على Cloudflare.
CDN وCache Components لصفحات المنتج؛ لا تصل كل الطلبات لقاعدة البيانات.
Medusa Stateless خلف Load Balancer، مع PgBouncer.
Redis للجلسات والـ Rate Limiting والطوابير.
فصل الكتابات الثقيلة (بريد، تحليلات، ولاء) عن مسار الدفع.
Idempotency يمنع الطلبات المكررة عند إعادة المحاولة.
Read Replica للكتالوج والتقارير عند الحاجة.
Load Test بـ k6 على 5× الحمل المتوقع قبل الإطلاق.
Partitioning للطلبات عند تجاوز عشرات الملايين، وليس قبل ذلك.
لا Microservices قبل أن تثبت المقاييس أن Monolith هو العنق.

-- updated_at triggers
do $$
declare
  r record;
begin
  for r in
    select table_schema, table_name
    from information_schema.columns
    where column_name = 'updated_at'
      and table_schema in ('catalog','engagement','commerce','content')
  loop
    execute format(
      'drop trigger if exists trg_touch_updated_at on %I.%I',
      r.table_schema, r.table_name
    );
    execute format(
      'create trigger trg_touch_updated_at
       before update on %I.%I
       for each row execute function ops.touch_updated_at()',
      r.table_schema, r.table_name
    );
  end loop;
end $$;

returns trigger
language plpgsql
as $$
begin
  raise exception 'loyalty_transaction is append-only';
end;
$$;

create trigger loyalty_transaction_append_only
before update or delete on engagement.loyalty_transaction
for each row execute function engagement.reject_loyalty_mutation();

B.9 قواعد التكامل والسلامة
القاعدة	التنفيذ
Waitlist لها هدف واحد فقط	num_nonnulls(civilization_id, product_id, drop_id) = 1
منع تكرار Waitlist لنفس الهدف	Unique expression index على (target, lower(email) or phone)
تقييم واحد لكل Order Item	unique(order_item_id)
تقييم موثّق فقط	الربط بـ order_item + حالة approved بعد التسليم
منع البيع الزائد	حجز ذري في Medusa + drop_allocation للـ Drops
كل زجاجة محدودة	serial_unit فريد لكل variant + serial_number
الولاء غير قابل للتعديل	Trigger يمنع UPDATE/DELETE على loyalty_transaction
الدفع Idempotent	ops.idempotency_key + ops.webhook_event(provider, event_id)
الأحداث الجانبية	ops.outbox_event بدلاً من البريد внутри طلب الدفع
نمط حجز الـ Drop (SQL فقط، ليس API):

update engagement.drop_allocation
set reserved_quantity = reserved_quantity + $1,
    version = version + 1
where drop_id = $2
  and variant_id = $3
  and quantity - reserved_quantity >= $1
returning drop_id, variant_id, reserved_quantity, version;
إذا أعادت zero rows، فهذا يعني نفاد التخصيص، ولا يتم إنشاء الطلب.
